# Load/Save 패킷 통합과 서버 부하 분석

> **문제:** DB 저장과 캐릭터 로드가 겹치는 상황에서 일시적인 지연과 처리 정체가 관찰되었습니다.  
> **접근:** DB 연결 방식과 패킷 흐름을 구분하여 살펴본 후, 저장 패킷을 묶어 작업량의 집중을 줄였습니다.

[← 대표 사례 목록](../README.md) · [당시 작업 원본](../DevReport/2025_09_25_Load개선.md)

## 1. 문제와 관찰

게임 서버의 Load/Save 지연을 추적하면서 연결과 프로시저 자체의 시간뿐 아니라, **Save 요청 패킷이 특정 시점에 몰리는 현상**을 함께 살펴봤습니다.

당시 기록에 남아 있는 관찰값은 아래와 같습니다.

| 관찰 항목 | 당시 기록 |
| :--- | :--- |
| 개별 Load/Save 프로시저 반복 호출 시험 | 약 **30ms** 수준으로 안정적인 구간 관찰 |
| 로그인/로그아웃을 포함한 로드 흐름 | 평소 **80~100ms**, 간헐적으로 **200ms 이상** |
| SaveDB 작업과 버퍼 적체가 겹친 사례 | 최대 **약 700ms** 지연 관찰 |
| 저장 요청 구조 | 캐릭터당 짧은 구간에 **20개 이상의 저장 패킷** 처리 |

**해석:** DB 연결 방식만 바꾸는 것으로 차이가 뚜렷하게 드러나지 않았으며, **요청이 집중되는 시점의 메시지/저장 처리 흐름**도 분석할 필요가 있었습니다.

## 2. 시도한 개선

서로 분리되어 있던 저장 관련 메시지를 통합하여, 해당 작업에서 전달하는 SaveDB 패킷 수를 **21개에서 3개로 줄였습니다.**

```text
Before: Multiple save requests (21)
                  ↓
           SaveDB processing

After:  Consolidated requests (3)
                  ↓
           SaveDB processing
```

목표는 단일 SQL 호출 시간을 줄이는 것만이 아니라, **동시에 유입되는 저장 메시지의 처리 부담을 낮추는 것**이었습니다.

## 3. 테스트 결과

당시 메모에는 약 **2,000개의 더미 접속을 이용한 반복 시험**이 기록되어 있습니다.

- 기존 구조에서는 Load/Save 처리가 겹칠 때 약 **1,500회 부근**에서 정체를 관찰했습니다.
- 패킷 통합 후에는 비슷한 문제가 약 **1,800회 부근**에서 나타났다고 기록했습니다.
- 당시에는 순간적인 메시지 처리 여유가 **대략 20~30% 개선된 것으로 추정**했습니다.

**측정상의 한계:** 위 수치는 당시 개발 환경에서의 관찰 결과이며, 통제된 벤치마크의 처리량·p95/p99 지연 지표는 아닙니다. 20~30%도 검증된 범용 성능 향상 수치로 사용하지 않습니다. 정체가 발생한 근본 원인이 모두 제거되었다고 단정할 수도 없습니다.

## 4. 배운 점

1. DB 연결이나 특정 프로시저를 단독으로 측정한 결과가 **실제 서비스 흐름의 지연을 그대로 설명하지는 않습니다.**
2. 개별 연산의 평균 실행 시간만큼 **메시지 수와 순간 집중도**가 중요할 수 있습니다.
3. 성능 개선을 주장하려면 **동일한 부하 조건, 반복 측정, 분포 지표, 장애 재현 여부**를 함께 확인해야 합니다.

**후속 과제:** 동일 조건에서 Load/Save 지연 분포를 비교하고, 패킷 통합 전후의 큐 길이·처리 시간·재시도/실패 패턴을 추가로 측정할 필요가 있습니다.
