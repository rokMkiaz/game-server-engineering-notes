# TVP 도입 검토에서 JSON 배치 저장으로 전환한 과정

> **문제:** 많은 Row 데이터를 개별 프로시저 호출로 저장하면 호출 수가 늘어 성능·운영 부담이 생깁니다.  
> **선택:** TVP(Table-Valued Parameter) 적용을 먼저 검토했지만 기존 DB 연동 라이브러리 제약 때문에, JSON 기반 일괄 처리로 방향을 변경했습니다.

[← 대표 사례 목록](../README.md) · [당시 작업 원본](../DB최적화.md)

## 1. 배경

게임 서버에서 여러 Row 데이터를 저장할 때 개별 항목마다 DB 프로시저를 호출하는 방식은 호출 횟수가 많아질수록 부담이 될 수 있습니다.

당시 개선 목표는 **여러 항목을 하나의 요청으로 전달하고 DB에서 집합적으로 처리하는 것**이었습니다.

## 2. 첫 번째 선택지: TVP

SQL Server의 TVP는 여러 행을 테이블 형태의 파라미터로 전달할 수 있어 적합한 대안으로 검토했습니다. 이를 위해 서버 측 바인딩 구조와 SQL의 사용자 정의 테이블 형식, MERGE 기반 처리 예시를 실험했습니다.

다만 당시 프로젝트에서 사용 중이던 **구버전 DB 연동 라이브러리와 바인딩 구조의 제약**으로 TVP를 곧바로 적용하기 어려웠습니다. 기존 연동 계층 전체를 업데이트하기도 쉽지 않은 상황이었습니다.

**중요:** 이 과정은 TVP 자체가 비효율적이라는 뜻이 아닙니다. 기존 프로젝트 환경에서의 호환성·변경 비용 때문에 채택하지 못한 사례입니다.

## 3. 대안: JSON 기반 배치 처리

다음으로 여러 Row 데이터를 JSON 형태로 직렬화하고, SQL Server에 큰 문자열 파라미터로 전달한 뒤 한 번의 프로시저 실행에서 처리하는 방식을 선택했습니다.

```text
Server Row Data
     ↓  serialize
JSON payload (one parameter)
     ↓  one stored procedure call
SQL Server
     ↓  parse / set-based processing
Insert / Update
```

작업 기록에 따르면 **수백 건의 데이터를 한 호출에 전달**할 수 있도록 구성하고, 서버 코드에서는 재사용하기 쉽도록 JSON 직렬화 로직을 템플릿 형태로 다루었습니다.

## 4. 기술적 판단과 한계

| 기준 | TVP | JSON 배치 처리 |
| :--- | :--- | :--- |
| 데이터 표현 | 구조화된 테이블 파라미터 | 문자열 직렬화 |
| 당시 프로젝트 적합성 | 레거시 바인딩 제약으로 적용 곤란 | 기존 호출 구조를 활용하기 상대적으로 쉬움 |
| 장점 | 명시적인 테이블형 입력 | 호출 통합 및 변경 범위 축소 |
| 추가 고려사항 | 기존 연동 계층 호환성 | JSON 파싱 비용, 입력 검증, 크기 제한, 오류 처리 |

**검증 범위:** 이 문서는 당시 설계 선택과 구현 방향을 설명합니다. TVP 대비 JSON의 성능 우위를 입증한 결과나 정확한 호출 시간 개선율은 기록에 없으므로 주장하지 않습니다.

## 5. 배운 점

- 좋은 기술이라도 **기존 시스템의 라이브러리와 운영 제약**에 맞지 않으면 채택하기 어렵습니다.
- DB 호출을 줄이는 것과 DB 내부 파싱·처리 비용은 **별도로 측정**해야 합니다.
- 배치 저장에는 일부 실패, 중복 요청, 트랜잭션 경계, 동일 키 충돌에 대한 검증이 필요합니다.

**후속 과제:** 같은 데이터셋에서 개별 호출과 JSON 배치의 총 처리 시간 및 DB 부하를 비교하고, 장기적으로는 드라이버/바인딩 계층 개선 가능성도 평가할 수 있습니다.
