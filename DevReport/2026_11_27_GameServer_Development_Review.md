# 게임 서버 개발 작업 정리 — 저장 흐름 개선과 운영 도구

> 정리일: 2026-11-27  
> 기존 공개 작업 기록과 본인이 설명한 프로젝트 업무를 바탕으로 정리한 보고서입니다. 정리일은 구현·배포 완료일이 아니며, 모든 작업을 최근 한 기간에 수행했다는 뜻은 아닙니다. Load/Save 수치는 2025-09-25 기록의 관찰값입니다.

## 1. 프로젝트별 업무 범위

| 프로젝트 | 본인이 설명한 작업 |
| :--- | :--- |
| 천상비M | 통합 서버(유니온) 구축, 월드 공성전, 해외 서버 구축 |
| 메틴M | 공성, 월드 구축 |

천상비M2도 참여 프로젝트로 언급했으나, 이번에 확인한 본인 설명만으로는 구체적인 담당 범위를 확정하기 어려워 세부 업무를 추가하지 않았습니다. 아래 개선 작업 역시 특정 게임에 귀속된다는 근거가 충분하지 않아 공통 기술 기록으로 정리합니다.

## 2. Load/Save 처리 흐름 분석과 저장 패킷 통합

### 문제와 원인 분석

캐릭터 로드와 저장이 겹치는 구간에서 지연과 처리 정체가 관찰되었습니다. DB 연결 방식과 개별 프로시저 호출을 확인한 뒤, 실제 로그인·로그아웃 흐름에서 저장 요청이 집중되는 상황을 별도로 살펴봤습니다.

| 당시 측정 대상 | 기록된 관찰 |
| :--- | :--- |
| Load/Save 프로시저 반복 호출 | 약 30ms 수준의 안정적인 구간 |
| 로그인·로그아웃을 포함한 로드 흐름 | 평소 80~100ms, 간헐적으로 200ms 이상 |
| 버퍼 적체와 저장 작업이 겹친 사례 | 약 700ms 지연 |
| 저장 메시지 | 캐릭터당 짧은 구간에 20개 이상 집중 |

측정 범위가 서로 다르므로 위 시간을 직접적인 전후 성능 비교로 사용하지 않습니다. 연결 방식 변경만으로 뚜렷한 차이가 확인되지 않았으며, 요청의 순간 집중도와 처리 흐름도 분석 대상이 되었습니다. 저장 지연과 로드 지연의 상호 증폭은 원본에서도 추가 검증이 필요한 가설로 남았습니다.

### 변경한 내용

분리된 저장 메시지를 묶어 해당 SaveDB 경로의 패킷 수를 **21개에서 3개로 줄였습니다.** 목적은 순간적으로 유입되는 메시지 처리 부담을 낮추는 것이었습니다. 이 수치는 저장 프로시저 호출 수나 DB 처리 시간이 같은 비율로 줄었다는 의미는 아닙니다.

### 검증 결과와 한계

약 2,000개의 더미 접속을 활용한 당시 시험에서는 Load/Save가 겹칠 때 정체가 관찰되는 지점이 기존 약 1,500회 부근에서 변경 후 약 1,800회 부근으로 이동했습니다. 변경 후에도 정체는 발생했습니다.

원본의 20~30% 개선 추정은 통제된 처리량 벤치마크가 아니므로 확정 성과로 제시하지 않습니다. 반복 횟수별 결과, 지연 분포, 하드웨어·부하 조건이 충분히 정리되어 있지 않아 서비스 전체 성능 향상이나 근본 원인 제거를 단정할 수 없습니다.

## 3. 레거시 DB 연동 제약에 맞춘 JSON 배치 저장

### 문제와 선택

여러 행을 개별 프로시저 호출로 저장하는 구조에서 호출을 통합하는 방안을 검토했습니다. TVP 적용을 먼저 실험했지만, 당시 DB 연동 라이브러리와 바인딩 구조의 호환성·변경 비용 때문에 바로 도입하기 어려웠습니다.

### 구현 방향

여러 행을 JSON으로 직렬화해 문자열 파라미터로 전달하고, 하나의 프로시저 실행에서 파싱·집합 처리를 수행하는 방식을 선택했습니다. 공개 기록에는 수백 건의 데이터를 한 호출로 전달하도록 구성하고 직렬화 로직을 재사용 가능한 템플릿 형태로 다룬 내용이 남아 있습니다.

### 검증 범위

확인되는 것은 호출 통합 방식과 구현 방향입니다. TVP보다 JSON이 빠르다는 비교 결과나 정확한 처리 시간 개선율은 확인되지 않습니다. JSON 파싱 비용, 입력 크기, 부분 실패 및 트랜잭션 경계는 추가 검증 항목입니다.

근거: [JSON 배치 저장 사례](../case-studies/sql-json-batch-fallback.md), [DB 최적화 원본](../DB최적화.md)

## 4. 게임 서버 종합관리툴 개발

### 해결하려던 문제

서버 점검, SQL Server 관리, MongoDB 로그 조회, 캐릭터·아이템 관리가 여러 도구에 분산되어 있었습니다. 기존 서버와 저장 구조를 유지하면서 운영 작업을 한 화면에서 수행할 수 있도록 Python/Flask 기반 관리 도구를 개발했습니다.

### 공개 기록으로 확인되는 구현

- 서버 환경 선택, 상태 조회, 점검 체크리스트와 운영 명령 연동
- SQL Server 용량·인덱스 조회, 백업, 환경 간 스키마·프로시저 비교
- MongoDB 로그 검색·필터, 별칭 및 인덱스 관리
- 계정·캐릭터·아이템 데이터 조회·관리
- 기존 바이너리 데이터의 디코딩 → 조회·수정 → 규칙 검증 → 인코딩
- 로그인·역할 및 메뉴·세부 기능별 권한 판별

기존 바이너리 저장 구조와 서버 호환성을 유지하는 대신, 관리 도구의 변환 로직과 게임 데이터 규칙을 함께 관리해야 하는 제약을 받아들였습니다. AI는 반복적인 연동 코드와 기능 확장을 돕는 도구로 활용했습니다.

### 결과와 남은 한계

분산된 관리 기능을 통합한 구현 범위는 공개 문서에서 확인할 수 있습니다. 다만 운영 시간 단축률이나 오류 감소율은 측정 근거가 없어 수치로 제시하지 않습니다. 관리 UI 통합만으로 보안이 보장되는 것도 아닙니다. 바이너리 포맷 확장성과 호환성, 변경 작업의 권한·감사·복구 검증은 계속 다뤄야 할 과제입니다.

근거: [종합관리툴 상세 기록](../projects/integrated-game-server-admin-tool/README.md)

## 5. 후속 검증 과제

아래는 완료된 성과가 아니라 추가로 확인할 항목입니다.

- 동일 조건에서 Load/Save 변경 전후의 지연 분포, 큐 길이, 정체 재현 여부 비교
- 동일 데이터셋에서 개별 저장과 JSON 배치 저장의 총 시간·DB 부하·오류 처리 비교
- 바이너리 데이터 변환의 왕복 일치와 버전 호환성 검증
- 운영 도구의 대상 선택, 권한 거부, 실패·복구 시나리오 및 작업 시간 측정

## 6. 기록 및 공개 범위

이 보고서는 기존 문서의 구현·관찰·가설을 구분해 요약했습니다. 프로젝트별 업무는 본인의 설명 범위로 한정했으며, 이전 대화에서 생성된 경력 초안의 추가 세부사항을 검증된 사실로 사용하지 않았습니다.

상용 서버 원본 코드, 접속 정보, 계정·실사용자 데이터, 내부 운영 설정, 상세 제어 프로토콜, 원본 화면·영상 및 사고 경로는 포함하지 않았습니다. 기존 기록은 보존하며, 이 문서의 추가를 기존 문서 전체에 대한 보안 검수로 해석하지 않습니다.
